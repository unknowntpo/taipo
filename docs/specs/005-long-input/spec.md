# Spec 005: 長句自動送出

Status: Draft（2026-10-19，依使用者回報；待 human 審查）
Date: 2026-10-19
Traceability: enforced
Builds on: Spec 001–004

## Intent

一口氣打一整句注音（超過 32 鍵），不會整句變回原始按鍵；前面已確定的詞自動送出，只有真正解析不了的鍵維持原樣。

## Evidence

2026-10-19 使用者回報：打「今天的天氣很好很適合出門運動喔」得到 `rup wu0 2k7wu0 fu4cp3cl3cp3g4ck6tj ap6m/422j/4i`。重現：47 鍵超過 Spec 001 F2 的 32 鍵上限，只回原文；前 30 鍵本身可解出「今天的天氣很好很是」。

## Example

| 按鍵 | 之前 | 之後 |
| --- | --- | --- |
| `rup␣wu0␣2k7wu0␣fu4cp3cl3cp3g4ck6tj␣ap6m/422j/4i` + Enter | 整串原文 | 打字途中送出「今天的天氣很好」，Enter 送出「很適合出門用動i」（`22` 多按一鍵已修正；`i`＝ㄛ 未按聲調，保留原樣） |

## Behavior

1. **自動送出**：每次按鍵後，若組字區超過 24 鍵，送出第一名候選最前面、結束位置不超過「總鍵數 − 12」的完整詞段（不含尾巴）；組字區保留其餘按鍵並重新解碼。送出的部分不學習，`previousLanguage` 設為最後送出詞段的語言。
2. **詞段位置**：候選的每個詞段記錄它在按鍵中的結束位置（中文句、混合、尾巴）。
3. **保底候選**：輸入至少 12 鍵、整段解析不了、且已解析的前段超過一半時，提供「最長已解析前段＋其餘原始按鍵」的候選，排在所有完整候選之後、原文之前。
4. **尾巴可接在修正過的前段後**（放寬 Spec 003 X7），但要多扣一次編輯懲罰，避免「刪掉一個真正的鍵再留尾巴」（`xu3ge` → 理e）勝過一鍵修正（理事）。

## Acceptance

### Behavior
- L1：具名測試：使用者的句子送出內容以「今天的天氣很好很」開頭、不含原始按鍵開頭。
- L2：具名測試：逐鍵打字時組字區不超過 24 鍵（且確實長過 12 鍵，正向對照）。
- L3：具名測試：短輸入（18 鍵）不自動送出，組字區顯示「今天的天氣」。
- L5：見 Spec 003 case `tail-after-fixed-prefix`。

### Failure and retry
- L6：短的無法解析輸入（`123`、`JI3`、`3333`）仍只有原文（既有 Spec 001／002 case rows）。
- L7：[measure] 1,700 筆注音鄰鍵錯字與 Spec 003 前版本相比，第一名差異不增加（2026-10-19：1 筆，即已知的 `w8 apt`）。

### Budget
- L4：[measure] 逐鍵打完使用者的 47 鍵句子，每鍵 p95 ≤ 16 ms。`taipo-bench latency`。2026-10-19 量測時系統負載平均 110（OrbStack 佔 271% CPU），改動前後的版本都超標（15–42 ms），需在系統閒置時重測。

### Observability
- L8：[manual] 送出的詞段在 IME 中即時出現在游標前。

## 簡化審查

1. **質疑需求**：自動送出（使用者回報）、保底候選（同一句的後半有錯字，否則仍整段原文）、尾巴放寬（同上）。
2. **刪除**：提高 32 鍵上限（解碼成本隨鍵數增加，且模糊修正上限以整段計，長句錯字一多仍失敗）。
3. **簡化**：沿用現有詞段資訊，只加結束位置。
4. **縮短驗證週期**：全部為 session 單元測試。
5. **自動化**：無。

## Non-goals

- 送出後再回頭修改已送出的字。
- 依標點自動斷句。
